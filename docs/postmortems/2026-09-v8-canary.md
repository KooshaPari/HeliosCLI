# 2026-09 v8-canary: never green, treated as informational

## Summary

The `v8-canary` GitHub Actions workflow has not produced a green run on this repo since
[PR #13366](https://github.com/KooshaPari/HeliosCLI/pull/13366) (Mar 3, 2026) switched the bzlmod
LLVM toolchain from `toolchains_llvm` to `toolchains_llvm_bootstrapped` and orphaned every
`@llvm//…` label in `.bazelrc` and the workflows. After four PRs that root-caused successive
layers of the failure, the deepest remaining blocker is a libc++ `include_next`-chain reordering
problem in the custom libc++ overlay (`third_party/v8/libcxx.BUILD.bazel` plus the
`patches/rusty_v8_libcxx_include_next.patch` overlay) for which no known-good configuration
exists.

The decision recorded here is to make `v8-canary` informational — the workflow continues to
build and capture a full log per target as an artifact, but its exit code does not fail the
job or block Mergify auto-merge on PRs.

## Why `v8-canary` has never been green

The workflow does a custom rust-v8 build via Bazel, with V8/ICU compiled against a libc++ that
lives inside the `rusty_v8` crate. Chromium's GN build defines `_GNU_SOURCE` globally; the
published prebuilt objects in `rusty_v8` were always compiled that way. To reproduce locally,
the build uses `-nostdinc++` and a hand-patched libc++ include directory
(`third_party/v8/libcxx.BUILD.bazel`), plus a chain of `patches/` overlay files that try to
rewrite the libc++ C headers so that glibc's `string.h` / `wchar.h` sit on the `include_next`
path after libc++'s shims.

There is no upstream Bazel module that solves this. The earlier branch
`fix/v8-canary-bazel-2026-08-08` (tip `cc4b91962`) spent a 325-line patch
(`patches/rusty_v8_libcxx_include_next.patch`) plus two more attempts (`9a5fa5615`,
`7b7f3314c`) on the same problem and never went green.

## Decision

`v8-canary` is now informational. Both the Bazel build step and the
downstream Stage / Smoke steps are wrapped in `tee` and marked
`continue-on-error: true`. The Stage step needs `dist/<target>/` to
exist; without it, it fails on `find` (not on a Bazel error). Without
`continue-on-error: true` on Stage and Smoke, the job still fails even
when the Build step's `exit 0` worked — caught in run 35480449768,
where Build exited 0 with the expected warning annotation but Stage
still failed. The full build log is always captured to
`${RUNNER_TEMP}/v8-canary-${TARGET}-${SANDBOX}/bazel-build.log` and
uploaded as an artifact (`*-log`) so the next person to tackle the
libc++ `include_next`-chain problem has a fresh failure log to start
from. The artifact upload steps are also `continue-on-error: true` so
the job does not fail when there are no `dist/` artifacts to upload.

`.mergify.yml` is updated with a comment block that explicitly records this decision; the
required-checks list (`CI results (required)`, `Lint & Format`, `build + test + clippy + fmt`)
remains unchanged.

## What does NOT change

- The label fixes in PRs #676, #677, #678 are real and should be kept. They move the build
  failure from `Bazel option-loading (8 s)` into `V8 compile (112 s)`, which is a real
  improvement for anyone trying to debug the include-order problem locally.
- `rusty-v8-release.yml` is not changed. It is tag-triggered, never gates `main`, and shares
  the same `--platforms=@toolchains_llvm_bootstrapped//platforms:${PLATFORM}` label fix as
  `v8-canary.yml`. The label is already correct on `origin/main`.
- The `fix/v8-canary-bazel-2026-08-08` branch is left alone. None of its three libc++
  `include_next`-chain patches should be imported until someone has the time to bisect them
  against the current `third_party/v8/{BUILD.bazel,libcxx.BUILD.bazel,libcxxabi.BUILD.bazel}`
  configuration.

## Re-enabling `v8-canary` as a hard gate

If and when the libc++ include-order problem is solved, revert this commit and uncomment
`check-success=v8-canary` in the `.mergify.yml` "Auto-merge when CI is green" rules.
